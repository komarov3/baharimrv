# Role provisioning fix, Gazi Bay seed, activity detail screen, and Mirasi UI pass

This diff fixes signup role provisioning (moving cap issuance from a fire-and-forget goroutine to a synchronous call with a 202 path), adds the Gazi Bay / Hamisi Mwangi demo project seed, wires a new `GET /activities/:id/detail` backend endpoint, and ships the Android `PlantingDetailScreen` that taps into it. A broad Mirasi wireframe CSS pass updates class names across the web frontend, and the Android `WalletScreen` and `ProfileScreen` receive visual redesigns. Firebase Analytics and Crashlytics are also added to the Android build.

Watch for: (confirmed) two silent `_ = s.db.Model(...)` discards survive in `identity/service.go` at lines 139–142, though these are in the pre-existing `fail()` helper rather than in the functions targeted by the fix — the FEAT-001 spec required fixing `IssueCapForUser` and `IssueMonitorCapForUser` only. (confirmed) cross-role cap issuance in `auth/service.go` line 131 is still dispatched as `go s.identity.IssueCapForUser(...)`, meaning hub-resolved role upgrades at login time retain the fire-and-forget race that the primary signup path now avoids. (confirmed) photo rendering on the activity detail screen is blocked by the absence of a backend media URL in the detail response; the ViewModel now fetches media via the separate `/monitoring-records/evidence/:id` route and decodes it locally, so actual photos are rendered — this resolves the gap flagged in the prior iteration. (possible) `mw-btn.g` CSS selector is written with a dot literal in JSX `className` attributes across the web; `mw-btn.g` is a descendant selector in CSS, not a modifier class — the green button styling may not apply.

**Verdict**: NEEDS_CHANGES

## High-level view

The signup provisioning fix closes the main regression: cap issuance now blocks the registration response and returns 202 with `capIssuanceFailed: true` if the chain call fails, giving the client something to act on rather than silently succeeding with no session token. The reload-and-set-identity path after synchronous cap issuance is also new and means the returned identity object reflects the cap that was just issued, which matches what a caller observes at the first login. The fix is scoped correctly to the primary signup path; hub-resolved cross-role upgrades at login time still fire as a goroutine.

The Gazi Bay seed creates Hamisi Mwangi as manager, seeds two plots, and anchors the first activity's provenance. The idempotency check guards re-runs, though its guard condition — whether any `ConservationProject` with that name exists — means a torn state (manager exists, project does not) would skip the entire block rather than resuming from where it stopped.

The Android `PlantingDetailScreen` and its ViewModel are the most significant new surface. The prior iteration's placeholder-only evidence rendering is resolved: the ViewModel now calls the `/monitoring-records/evidence/:id` streaming endpoint (which the backend has exposed since the base branch), decodes the image on `Dispatchers.IO` with downsampling, and the screen renders either the bitmap thumbnail or a dashed placeholder while loading. The on-chain link section renders a green "View on IOTA ↗" button launching `ACTION_VIEW` only when `explorerUrl` is non-null.

The Mirasi CSS pass introduces a new `mw-*` utility class set and applies it across several web pages and the Android `WalletScreen`/`ProfileScreen`. The CSS selector `.mw-btn.g` is syntactically a descendant selector (`.mw-btn` containing an element `.g`), not a modifier class. JSX `className="mw-btn mw-btn.g"` passes a literal string with a dot, which browsers will not match as a class token — the green button variant will not apply in those places.

Firebase BoM 34.14.1 and the `google-services` plugin are added without a corresponding `google-services.json` tracked in the repository diff; the file appears as untracked. This is fine for a dev device build but blocks CI assembly if the file is absent.

1. **`mw-btn.g` invalid as a CSS class** — `.mw-btn.g` in `styles.css` is a descendant selector, not a utility modifier. JSX `className="mw-btn mw-btn.g"` passes a class token `mw-btn.g` which browsers cannot match against a rule written `.mw-btn.g`. Rename to `mw-btn--g` (or `mw-btn-g`) in both the CSS file and all JSX call sites.

2. **Cross-role cap issuance still async at login** — `auth/service.go` line 131 dispatches hub-resolved cross-role upgrades as `go s.identity.IssueCapForUser(...)`. If a user's role is promoted by hub resolution on their first login, the cap write races the session being returned. Apply the same synchronous + `capIssuanceFailed` pattern used for the primary signup path, or add a comment explaining why the race is acceptable here.

3. **Gazi Bay seed torn-state gap** — The idempotency guard in `runGaziBay` counts `ConservationProject` rows by name. If the seed was partially applied (manager created, project row absent), the guard returns early and leaves the manager account without a project. Make the guard check the manager account's existence and resume from the next unfinished step, or use a transaction around the whole block.

4. **`google-services.json` untracked** — Firebase requires `google-services.json` at build time. It is listed as untracked in `git status`. If it is intentionally excluded (contains API keys), CI must have a secrets-injection step before `assembleDebug` or the build will fail. Document this requirement in the project README or `BAHARILINK_SETUP.md`.

### Synchronous cap issuance at signup, with a surviving async path at login

The core signup fix in `auth/service.go` replaces `go s.identity.IssueCapForUser(...)` with a synchronous call, captures the bool result, reloads the provision immediately after, and sets `result.Identity` to the freshly loaded provision. When `capOK` is false, the handler returns 202 with `capIssuanceFailed: true` and no session token — previously this path would have returned 201 with a session but an unpopulated capability. The handler change in `handlers.go` gates on the new `result.CapIssuanceFailed` field before the existing `errors.Is(err, ErrProvisioning)` block, so both code paths remain distinct.

The cross-role upgrade path in the same `Register` function (line 131) still runs as a goroutine: when `ResolveRoleFromHub` returns a role different from the one the user registered with, the new cap is issued asynchronously. This is a narrower case (hub-reconciled role promotion, not initial provisioning), but it retains the race that the fix was meant to address for the primary case. It is not a regression — this code existed before the diff — but it is worth flagging since the same user-visible symptom (no capability despite a successful login) can appear through this path.

### Planting activity detail: evidence media rendering

The ViewModel's `loadImage` method calls `repository.evidenceMedia(evidenceId)` mapped to `@GET("api/v1/monitoring-records/evidence/{id}")`. The response body is decoded on `Dispatchers.IO` with `BitmapFactory.Options.inSampleSize` downsampling — important on phones where a full-resolution field photo could OOM. The screen shows a dashed `BahariDashedBox` placeholder while `state.image` is `Loading`, then the decoded bitmap once available, and the full-screen overlay on tap.

### Mirasi CSS: `.mw-btn.g` selector is broken

In `styles.css`:
```css
.mw-btn.g { background: var(--mirasi-green); ... }
```

In JSX (e.g. `VerificationPage.tsx`, `PlantingActivityPage.tsx`, `CreditsPage.tsx`):
```jsx
className="mw-btn mw-btn.g"
```

A CSS class token cannot contain a dot. The browser sees `mw-btn.g` as a single class name and `.mw-btn.g` as "element with class `mw-btn` that is also a descendant of element with class `g`" — neither matches. All green primary buttons in the web frontend will render with the default white/border style. The fix is a one-character rename: `.mw-btn--g` in CSS, `mw-btn mw-btn--g` in JSX.

### Firebase addition without tracked config

`android/app/build.gradle.kts` adds `firebase-analytics` and `firebase-crashlytics` via the Firebase BoM 34.14.1. The `google-services.json` appears in `git status` as untracked. This is expected for a file containing API keys, but it is a CI concern: if the build agent does not inject the file, `assembleDebug` will fail with a Gradle plugin error. The FEAT verification evidence was captured on a local machine where the file was present.
