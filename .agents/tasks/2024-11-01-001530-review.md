# Android UI redesign against wireframe conservation module (C1-C4)

The Android app screens were redesigned to match wireframe specifications C1 through C4, which define the visual layout, component hierarchy, and information architecture for the conservation module. The redesign preserves all existing functionality while elevating visual fidelity, typography, spacing, and component composition to match the wireframe's professional design standard.

**Verdict**: NEEDS_CHANGES

## Watch for:

- **GPS badge positioning mismatch (confirmed)** — MonitorScreen displays GPS status as a StatusChip in the header row alongside "Synced", but wireframe C2 shows it inline with Plot P-14, attached directly to the plot context. The badge appears in the wrong section.
- **Missing queue indicator in header (confirmed)** — MonitorScreen header should show "6 queued" as a pill in the header per C2, not just sync count logic. Current implementation shows sync status but doesn't match the C2 visual treatment.
- **Verification stage detail format gap (likely)** — VerificationStage displays detail as "Plot records · monitors" but wireframe C3 specifies "312 plot records · 14 monitors" with explicit counts using middle dot separators. Implementation lacks the numeric precision shown in wireframe.
- **Revenue stream amount hardcoded (confirmed)** — HomeScreen wallet section displays placeholder amounts ("$1,214", "$8,900", "$6,068") as literal strings, not data-driven values from dashboard DTO. Production data won't flow through.
- **NDVI status placement (possible)** — HomeScreen shows NDVI status after the map, but wireframe C1 suggests it should be integrated with the map schematic itself, possibly as an overlay badge. Current placement may not match intended visual hierarchy.

## High-level view

HomeScreen implements the C1 dashboard structure with map, 2x2 metrics grid, wallet revenue streams, and alert cards with severity indicators. The implementation correctly uses CompactMetricCard with adjusted typography (headlineMedium for numbers, labelMedium for labels) and enforces the 2x2 grid for the first 4 metrics via chunked(2). Wallet section displays three revenue streams using the new WalletRevenueStream composable with emerald-colored amounts. Alert cards include severity indicator dots using Icons.Default.Circle with color mapping.

MonitorScreen implements C2 field capture with GPS status badge, two-column survival measurement layout, compact form fields, evidence count indicator, and voice button with microphone icon. GPS locked badge appears as StatusChip with "GPS locked ±N m" format and POSITIVE tone. Evidence manifest shows count as "Geo-tagged photos · N | Voice · N" with bullet separators. The microphone icon is present on the voice recording button. Form fields use the existing CaptureField composable which maintains compact styling.

CreditsScreen implements C3 verification pipeline with StageNumberCircle showing numbered stages and checkmark overlays for completed stages. Each stage displays title, detail text, and status chip. The StageNumberCircle uses a 40dp Surface with either the stage number or a checkmark icon, conditionally styled based on completion. Documents display with IPFS hash format "ipfs://Qm..." in monospace. The C4 marketplace section shows listings with VerifiedBadge (green circle with white checkmark) next to vintage for verified projects, price formatted with formatPrice showing "$28 📦", and SDG co-benefits displayed as emoji icons "🌍🌊🌿". Retirement certificate uses enhanced formatting with large quantity display, dual retirement record section, and allocation display "community 60 · project 25 · platform 15 🔒".

Design system components WalletRevenueStream, VerifiedBadge, StageNumberCircle, and formatPrice were added to Common.kt and integrated across screens. Typography adjustments follow the plan: metric numbers use headlineMedium with Bold, labels use labelMedium, and spacing is consistent at 12dp between cards with 16dp internal padding.

## HomeScreen C1 dashboard implementation

HomeScreen follows the C1 wireframe structure: project header, GPS plots with NDVI overlay, compact 2x2 metrics grid, wallet revenue streams, and alerts with severity indicators. The DashboardContent composable organizes sections with SectionHeader components and 12dp vertical spacing.

**Metrics grid layout**

The first four metrics display in a 2x2 grid using `dashboard.metrics.take(4).chunked(2)`. CompactMetricCard renders each metric with labelMedium for the label, headlineMedium + Bold for the value number, bodyLarge for units, and an optional StatusChip. Additional metrics beyond the first four render full-width using MetricCard.

**Wallet revenue streams**

The wallet section uses WalletRevenueStream three times for "Tourism contributions", "Carbon credit sales", and "Community share (60%)". Each stream displays the label in bodyMedium gray on the left and the amount in headlineSmall bold emerald on the right. However, the amounts are hardcoded strings: `WalletRevenueStream("Tourism contributions", "$1,214")`. The DashboardDto doesn't appear to carry revenue stream data, so the implementation can't be data-driven yet. This is a blocking concern: production data won't populate the wallet section. The visual treatment is correct (emerald color, bold, right-aligned), but the data flow is incomplete.

**Alert severity indicators**

Each alert card displays a colored circle icon at the start using Icons.Default.Circle with a 12dp size. The color maps severity: error/critical to error color, warning to tertiary, else primary. The severity chip also displays on the right side of each alert.

**NDVI status display**

The NDVI status displays as a text line above the ProjectMap: `"Satellite NDVI: ${it.status} (source · timestamp)"`. This is accurate but doesn't match the C1 wireframe's visual treatment, which suggests a more prominent badge or chip integrated with the map itself. The current approach feels like metadata text rather than a status indicator. Wireframe C1 shows a compact pill-like element, possibly overlaying or adjacent to the map schematic. The status should probably use StatusChip for consistency with other status displays across the app.

**ProjectMap implementation**

ProjectMap renders GPS plots as circles with NDVI-based color intensity on a Canvas. Tapping a plot displays its details below the map.

## MonitorScreen C2 field capture implementation

MonitorScreen implements the C2 wireframe with header, sync button, plot/methodology card, GPS location card with locked badge, survival measurement card, and evidence manifest card. The layout follows a vertical LazyColumn with 12dp spacing and 16dp padding.

**GPS locked badge**

The GPS badge appears in the GPS location card header as `StatusChip("GPS locked ±${state.gpsAccuracy.ifBlank { "?" }} m", tone = ChipTone.POSITIVE)` when latitude and longitude are present. The format matches C2's "GPS locked ±18 m" but the badge placement differs from the wireframe. C2 shows the GPS badge inline with "Plot P-14" near the top of the screen, not inside the GPS card. The current placement breaks the visual association between GPS status and plot context. The badge should be in the plot & methodology section or in the main header row alongside the queue indicator.

**Queue indicator treatment**

The header shows a queue indicator as StatusChip with either "${state.pendingCount} queued" (WARNING tone) or "Synced" (POSITIVE tone). The logic is correct but the visual treatment doesn't match C2's prominent pill-in-header style shown in the wireframe ("6 queued" as a colored off-sync pill). The current implementation embeds it in a Row with the title, which is close, but C2 suggests the queue count should be the primary visual signal when records are pending. The button below the header shows "Sync N pending records" when enabled, which duplicates the information. The wireframe's approach is cleaner: one prominent queue indicator, one sync action button.

**Survival measurement layout**

Survival count fields (alive, planted, average height, species) use two-column Row layout with 8dp spacing: alive/planted in the first row, height/species in the second.

**Evidence manifest formatting**

Evidence count displays as `StatusChip("Geo-tagged photos · N | Voice · N")` when evidence exists. The format uses pipe separators for multiple evidence types. C2 wireframe shows "Geo-tagged photos · 3 screen" which suggests a simpler format without the pipe-separated voice count. The current approach is more informative (shows both counts) but doesn't exactly match the wireframe's minimalist "type · count" format. The bullet separator is correct, but "screen" suffix is missing. Minor visual inconsistency.

**Voice recording button icon**

The voice button includes `Icon(Icons.Default.Mic, contentDescription = null)` before the text. The button text toggles between "● Stop & attach voice" (recording) and "Record voice observation" (idle).

**Outpost label styling**

The "Hash anchors to CreditMRV contract on sync" text uses labelSmall with primary color and medium font weight. The visual styling approximates the C2 "Outpost label" specification.

**Form field compactness**

CaptureField uses OutlinedTextField with default padding and labelMedium for labels. The fields render compactly in two-column rows with 8dp horizontal spacing.

## CreditsScreen C3 verification pipeline

The verification pipeline section displays as a LedgerCard with title, subtitle, and four VerificationStage composables. Each stage uses StageNumberCircle with a number or checkmark, stage label, detail text, and status chip.

**StageNumberCircle implementation**

StageNumberCircle renders a 40dp Surface with conditional styling: completed stages show primary background with white checkmark icon (size 24dp), active/pending stages show surfaceVariant background with the stage number in titleMedium Bold.

**Stage detail format**

Each VerificationStage displays detail text like "Plot records · monitors" and "NDVI · Sentinel-2 tile matched". The C3 wireframe shows explicit counts: "312 plot records · 14 monitors". The implementation lacks this numeric precision—it displays generic labels rather than data-driven counts. The detail string should be formatted with actual numbers from the pipeline state. This is a confirmed gap: the detail format is structurally correct (middle dot separators) but lacks the specificity shown in the wireframe.

**Numbered stage progression**

The pipeline hardcodes four stages with numbers "1" through "4". Each stage checks `status.uppercase().contains("COMPLETE") || status.uppercase().contains("VERIFIED")` to determine completion. This is a simple heuristic that works for placeholder data but may not scale to real pipeline states. The status strings ("PENDING") are hardcoded, so the checkmarks won't appear until the data structure supports actual verification states. The visual layout is correct; data integration is placeholder-level.

**Documents section**

DocumentItem composables display document name, IPFS hash format "ipfs://Qm..." in monospace, and status chip. Each document renders in a Row with status on the right.

## CreditsScreen C4 marketplace listings

MarketplaceListingCard renders each listing with project name + verified badge, vintage/product type row, availability count, SDG co-benefits emoji, price display, and buy button.

**VerifiedBadge placement**

VerifiedBadge appears next to the project name when `listing.registry.status` contains "VERIFIED" or "ACTIVE". The badge is a 20dp Surface with extraSmall shape, primary background, and white checkmark icon (size 14dp). The badge renders inline in a Row with the project name and vintage.

**Price formatting with emoji**

Price displays using `formatPrice(listing.pricePerTonne)`, which returns `"$$value 📦"`. The price renders in headlineMedium + Bold + primary color. The package emoji is present.

**SDG co-benefits emoji display**

Co-benefits display as `"🌍🌊🌿 SDG co-benefits"` in bodySmall + primary color when `listing.coBenefits.isNotEmpty()`. The emojis are visible and convey the intended meaning.

**Buy button styling**

Buy button uses `Button` with fillMaxWidth and 48dp height. Material 3 Button defaults to primary color, which is emerald (#08775E) in the app theme. The text is "Buy credits".

**Listing card visual structure**

The card uses LedgerCard with project name/badge row at top, HorizontalDivider, then availability/price row at bottom. The row with availability on the left and price on the right creates balance. The buy button spans full width below. StatusChip for registry status appears top-right.

## RetirementReceipt C4 dual retirement display

RetirementReceipt displays a title row with "Retirement certificate" + status chip, large quantity display "X tCO₂e retired" in headlineMedium bold primary, HorizontalDivider, then dual retirement sections.

**Dual retirement record section**

The receipt shows "Dual retirement record" as a titleSmall + SemiBold header, followed by "Serial retired on registry AND burned on-chain" in bodySmall gray. The section uses KeyValue pairs for batch, chain reference, ledger, and timestamp. The reference display attempts the arrow format: `"retire #${serial.take(12)}... → registry ref: #..."` in bodySmall monospace. The truncation logic (take(12)) ensures long serials don't break layout.

**Allocation display**

The allocation line `"community 60 · project 25 · platform 15 🔒"` is hardcoded as a string literal. C4 shows this as a bullet-separated allocation breakdown with lock emoji. The visual treatment is correct (bodySmall, gray), but the data is static. If RetirementResultDto carries allocation fields, they should be used instead of the hardcoded string. This is similar to the wallet revenue issue: correct visual treatment, incomplete data flow.

**Quantity and certificate styling**

The quantity displays as `"${result.quantityTonnes} tCO₂e retired"` in headlineMedium + Bold + primary, which makes it the focal point of the certificate. The certificate title uses titleLarge + Bold. The status chip in the header row provides at-a-glance verification status.

## Design system components integration

Common.kt includes three new composables: VerifiedBadge (green circle + checkmark), StageNumberCircle (numbered badge with checkmark overlay), and WalletRevenueStream (label + emerald amount). The formatPrice helper formats amounts with emoji. The components follow Material 3 design system patterns with proper color roles (primary, onSurfaceVariant) and typography scale (headlineMedium, labelMedium).

Typography adjustments are applied consistently: CompactMetricCard uses headlineMedium + Bold for numbers and labelMedium for labels. Wallet amounts use headlineSmall + Bold. Price displays use headlineMedium + Bold. Small metadata uses bodySmall or labelSmall.

Spacing is consistent: cards use 12dp vertical spacing (Arrangement.spacedBy(12.dp)), internal card padding is 16dp (LedgerCard default), and row elements use 8dp spacing.

## Missing or incomplete elements

**Revenue stream data flow** — Wallet section in HomeScreen displays hardcoded amounts. DashboardDto needs revenue stream fields (tourismRevenue, creditRevenue, communityShare) or similar structure to populate the wallet section with real data. Without this, the wallet section is a visual mockup that won't reflect production state.

**Verification stage counts** — VerificationStage detail text should include explicit counts (plot records, monitors, etc.) from a data structure. The current implementation uses generic strings. The data model should expose these counts so detail text can be formatted as "312 plot records · 14 monitors".

**Allocation breakdown** — RetirementReceipt allocation display is hardcoded. If allocation data is available in RetirementResultDto, it should be used. If not, the hardcoded string is acceptable as a placeholder until backend provides breakdown.

**NDVI status visual treatment** — NDVI status displays as text below the map. C1 wireframe suggests more prominent badge treatment, possibly integrated with the map schematic. Consider using StatusChip instead of Text for consistency.

**GPS badge placement** — GPS locked badge appears in the GPS card header but C2 shows it inline with plot context near the top of the screen. The badge should move to the plot & methodology section or the main header.

**Queue indicator emphasis** — MonitorScreen queue indicator is present but not visually emphasized as C2 suggests. The wireframe shows "6 queued" as a prominent pill, possibly the primary header decoration when records are pending. Current approach buries it alongside the title.

**Evidence count format** — Evidence manifest shows "Geo-tagged photos · N | Voice · N" but C2 shows "Geo-tagged photos · 3 screen". The format should match exactly: type · count · "screen" (if photo). Minor inconsistency.

Visual fidelity to wireframe C1-C4 is high. The implementation preserves all existing functionality: navigation, form inputs, GPS capture, evidence attachment, sync, loading/error/empty states.
